# Proposal system tasks — конструктор и презентация

Документ для исполнителя (агента или человека). Цель — привести PRISMA (`kp-builder`) в соответствие с принципами сборки КП из эталонного репозитория `Isty-org/sales`: коммерческий ритм, архетипы, библиотека блоков, бренд и тон Isty.

Источник принципов (эталон): `Isty-org/sales` — `HUMANS.md`, `AGENTS.md`, `specs/proposal-system.md`, `specs/content.md`, `docs/DESIGN_SYSTEM.md`, `docs/PROPOSAL_COMPONENTS.md`, `docs/NEW_KP_INSTRUCTION.md`.

Правила для исполнителя:

- Перед началом задачи прочитай раздел целиком (контекст, изменения, критерий приёмки, downside).
- Одна задача = один PR/коммит, кроме явно связанных (PT02 → PT03 → PT04 идут цепочкой по одной модели данных).
- После каждой задачи: `npm run build` зелёный, `npm run lint` без новых ошибок.
- Если задача меняет Supabase schema / storage / build output / production env — обнови **Resource profile** в [docs/deploy-docker-caddy.md](deploy-docker-caddy.md) в том же коммите (требование `AGENTS.md`).
- Не выдумывать контент за клиента. Любой плейсхолдер должен быть явно нейтральным, а не ложным фактом (принцип `specs/content.md` эталона).
- Ссылки на строки валидны на момент написания. Если файл сдвинулся — искать по сигнатуре.

## Главный разрыв

Эталон `sales` собирает каждое КП как **нарратив из набора блоков под один из 6 архетипов**. PRISMA рендерит все КП через **один фиксированный плоский шаблон** ([src/components/proposal/PublicProposalView.tsx](../src/components/proposal/PublicProposalView.tsx)) с ~14 секциями в неизменном порядке. Поэтому PRISMA сейчас — «заполнитель анкеты», а не «конструктор» и не сильная «презентация».

Что у PRISMA **уже сильнее** эталона и что нельзя ломать: приватные ссылки, пароль/срок, трекинг событий (`view`/`package_selected`/`cta_clicked`), AI-импорт JSON, ретеншн-архив в Telegram.

Приоритет:

| Группа | Задачи | Когда делать |
|---|---|---|
| P0 — высокий импакт, низкий риск, ничего не ломает | PT01 | сразу |
| P1 — фундамент конструктора (цепочка по одной модели) | PT02, PT03, PT04 | второй подход |
| P2 — библиотека блоков убеждения | PT05, PT06, PT07, PT08, PT09, PT10 | после P1 |
| P3 — guardrails и доработки | PT11, PT12, PT13 | по необходимости |

## PT01 — Привести публичный шаблон к дизайн-системе Isty

**Категория:** презентация, бренд.
**Принцип эталона:** `docs/DESIGN_SYSTEM.md` — тёмная база, фиолетовый акцент, Onest, glass-поверхности, строка микро-доверия.
**Файлы:** [src/components/proposal/PublicProposalView.tsx](../src/components/proposal/PublicProposalView.tsx), [src/app/globals.css](../src/app/globals.css), [src/components/proposal/Ui.tsx](../src/components/proposal/Ui.tsx), [src/app/layout.tsx](../src/app/layout.tsx).

### Контекст

`README.md` обещает тёмную палитру «по мотивам isty.ist», но реальный публичный рендер — светлый `bg-paper text-zinc-950` с **emerald**-зелёным как основным акцентом (кнопки, рекомендованный пакет, иконки proof). Это не бренд Isty. Токены эталона:

| Токен | HEX | Роль |
|---|---:|---|
| `main` | `#020B14` | базовый фон |
| `accent` | `#8E44AD` | основной акцент/интерактив |
| `stepA` | `#E67E22` | вторичный акцент (точечно) |
| `stepM` | `#ECF0F1` | светлый нейтрал/текст на тёмном |

Шрифт — **Onest**. Поверхности — `glass`/`card-dark`/`card-white`. Под CTA — строка микро-доверия `•`.

### Изменения

1. Завести токены Isty в `globals.css` (CSS-переменные или Tailwind v4 `@theme`): `--accent: #8e44ad`, `--accent-warm: #e67e22`, `--ink: #020b14`, `--paper-light: #ecf0f1`.
2. В `PublicProposalView.tsx` заменить **все** `emerald-*` на брендовый акцент (`accent`). Это касается: выбранного пакета, бейджа «Рекомендованный пакет», иконок `CheckCircle2`/`ShieldCheck`/`Sparkles`, рамок.
3. Унифицировать карточки на один стиль (`glass-card`/`card-dark`), а не разрозненные `border-zinc-200 bg-white`.
4. Подключить Onest вместо текущего шрифта (см. PT08 в `optimization-tasks.md` про шрифты — не конфликтовать; здесь добавляется Onest как основной).
5. Добавить строку **микро-доверия** под главным CTA: настраиваемое поле (по умолчанию `Self-hosted • Данные остаются у вас • Решение работает без нас`). Хранить в `Proposal` как `trustLine?: string` или в `shareSettings`.
6. Тёмная/светлая тема: оставить `ThemeToggle`, но дефолт публичной страницы привести к брендовому виду (тёмный hero как минимум).

### Критерий приёмки

- На публичной странице нет ни одного `emerald-*` класса (`grep -rn "emerald" src/components/proposal/`).
- Акцент — `#8e44ad`. Под CTA видна строка микро-доверия.
- `npm run build` ОК, верстка не съехала на `/p/<slug>` и `/proposal/[id]/preview`.

### Downside / откат

- Чисто визуальная правка, данные не трогаются. Откат — `git revert`.

## PT02 — Блочная модель страницы (`blocks[]`)

**Категория:** архитектура конструктора. **Фундамент для PT03, PT04 и всех новых блоков.**
**Принцип эталона:** `specs/proposal-system.md` — «страница должна в основном импортировать готовые блоки и собирать композицию»; «разница не в том, нужен ли ритм, а в том, какой блок усиливается».
**Файлы:** [src/lib/types.ts](../src/lib/types.ts), [src/lib/proposal.ts](../src/lib/proposal.ts), [src/lib/proposal-ai.ts](../src/lib/proposal-ai.ts), `supabase/schema.sql`, [src/components/proposal/PublicProposalView.tsx](../src/components/proposal/PublicProposalView.tsx).

### Контекст

Сейчас `Proposal` — плоский набор фиксированных полей (`clientContext`, `clientProblem`, `deliverables[]`, `packages[]`, `processSteps[]`, `proofItems[]`, ...), а `PublicProposalView` жёстко рендерит секции в одном порядке и показывает пустые секции с заглушками «Будет уточнено». Нельзя выбрать набор, порядок и состав блоков под архетип.

### Изменения

1. Ввести типизированную блочную модель:

   ```ts
   export type ProposalBlockType =
     | "hero" | "summary" | "context" | "solution"
     | "deliverables" | "packages" | "comparison" | "timeline"
     | "whyUs" | "proof" | "assumptions" | "outOfScope"
     | "terms" | "nextStep"
     // новые (PT05–PT10):
     | "roles" | "problemSplit" | "openQuestions"
     | "roiCalculator" | "estimateConfigurator" | "variantPicker"
     | "media";

   export type ProposalBlock = {
     id: string;
     type: ProposalBlockType;
     order: number;
     visible: boolean;
     // данные блока — узкий тип по `type` (discriminated union)
     props: Record<string, unknown>;
   };
   ```

2. Добавить `blocks: ProposalBlock[]` в `Proposal`. **Совместимость:** существующие плоские поля сохранить; написать миграцию `proposalToBlocks(proposal)`, которая для старых КП строит дефолтный `blocks[]` из текущих полей в нынешнем порядке (поведение 1:1 с сегодняшним рендером).
3. `PublicProposalView` переписать так, чтобы он **маппил `blocks` по `order`/`visible`** на компоненты-рендереры блоков, а не хардкодил секции. Существующие функции (`Section`, `Insight`, `TwoColumnText`, `ListGrid`) переиспользовать как рендереры соответствующих типов.
4. Скрытые/пустые блоки **не рендерить** (убрать «Будет уточнено» как способ заполнять пустоту — это противоречит `content.md`).
5. Supabase: хранить `blocks` как `jsonb`-колонку в `proposals` (минимальная миграция, без новых таблиц). Обновить `proposal-store.ts` (гидрация/сохранение) и `supabase/schema.sql`.
6. `proposal-ai.ts`: научить импорт принимать `blocks` опционально; при отсутствии — собирать дефолт через `proposalToBlocks`.

### Критерий приёмки

- Старое КП (созданное до миграции) открывается **визуально идентично** прежнему рендеру.
- Новое КП хранит `blocks[]`; перестановка `order` меняет порядок секций на публичной странице.
- `npm run build` ОК. Обновлён Resource profile (добавлена `jsonb`-колонка).

### Downside / откат

- Самая крупная правка. Делать с миграцией-«мостом» (плоские поля + `blocks` сосуществуют один релиз). Откат — рендерить по старым полям, игнорируя `blocks`.

## PT03 — Редактор блоков (добавить / удалить / переставить / скрыть)

**Категория:** UX конструктора. **Зависит от PT02.**
**Принцип эталона:** `HUMANS §6` — менеджер осознанно выбирает блоки под вопрос клиента.
**Файлы:** [src/components/proposal/ProposalEditor.tsx](../src/components/proposal/ProposalEditor.tsx), [src/components/proposal/Ui.tsx](../src/components/proposal/Ui.tsx).

### Контекст

Сейчас редактор — линейный список `SectionCard` с фиксированными полями; управление структурой ограничено 3 тоглами (`showPrices`/`showTimeline`/`showComparisonTable`). Нет добавления/удаления/перестановки блоков.

### Изменения

1. Панель «Блоки КП»: список `blocks` с drag-and-drop (или кнопки ↑/↓), переключателем `visible`, удалением и дублированием.
2. Кнопка «Добавить блок» → меню доступных `ProposalBlockType` с короткой подсказкой «когда использовать» (взять формулировки из `PROPOSAL_COMPONENTS.md` эталона).
3. Форма редактирования блока зависит от его `type` (рендерить нужный под-редактор).
4. Превью ([src/app/proposal/[id]/preview/page.tsx](../src/app/proposal/[id]/preview/page.tsx)) отражает текущий состав/порядок блоков.

### Критерий приёмки

- Можно собрать КП из произвольного подмножества блоков в произвольном порядке и увидеть это в превью и на `/p/<slug>`.
- `npm run build` ОК.

### Downside / откат

- DnD-библиотека добавит вес бандла; можно начать с кнопок ↑/↓ без внешней зависимости.

## PT04 — Архетипы-пресеты

**Категория:** скорость сборки, коммерческая точность. **Зависит от PT02/PT03.**
**Принцип эталона:** `specs/proposal-system.md` «Рабочие архетипы»; `PROPOSAL_COMPONENTS §1.2` «разные типы продаж усиливают разные блоки».
**Файлы:** [src/lib/proposal.ts](../src/lib/proposal.ts), [src/app/proposal/new/page.tsx](../src/app/proposal/new/page.tsx), [src/components/proposal/ProposalEditor.tsx](../src/components/proposal/ProposalEditor.tsx).

### Контекст

Эталон выделяет 6 архетипов, каждый со своим набором усиленных блоков. PRISMA не предлагает выбора стартовой структуры.

### Изменения

1. Описать пресеты (массив `blocks` по умолчанию) под архетипы эталона:
   - операционный контур (роли, этапность, тарифы темпа, ROI);
   - стратегический проект (нарратив, состав решения, границы);
   - сравнение архитектур (variantPicker + comparison + roiCalculator);
   - пакет сервисов на платформе (assistantTabs/roles, proof, openQuestions);
   - пакетное предложение с быстрым запуском (media, timeline, comparison);
   - модульная смета (estimateConfigurator, scope, comparison).
2. На `/proposal/new` — выбор архетипа, который засевает `blocks[]`. По умолчанию — «стратегический проект» (ближе к текущему шаблону).

### Критерий приёмки

- Создание КП из архетипа сразу даёт релевантный набор блоков, который дальше редактируется (PT03).
- `npm run build` ОК.

### Downside / откат

- Пресеты — данные, не логика. Откат — оставить один дефолтный пресет.

## PT07 — Открытые вопросы + статус «факт / допущение / вопрос»

**Категория:** библиотека блоков + контентная честность. **Зависит от PT02.**
**Принцип эталона:** `PROPOSAL_COMPONENTS §3.2` (`OpenQuestionsList` — «честная рамка неизвестности продаёт сильнее искусственной определённости»); `specs/content.md` — допущения помечаются, выдумки запрещены.
**Файлы:** новый рендерер + редактор; `types.ts` (рядом с `assumptions`/`outOfScope`).

### Контекст

Есть `assumptions[]` и `outOfScope[]`, но **нет открытых вопросов** и ничто не отличает подтверждённый факт от допущения/вопроса.

### Изменения

1. Блок `openQuestions`: список `{ question, note? }`.
2. Ввести лёгкую маркировку статуса для пунктов допущений/вопросов (`fact | assumption | open`), отрисовывать бейджем.
3. Под-редактор; рендерер честно показывает зону неизвестности, а не маскирует её.

### Критерий приёмки

- На странице видно, что является допущением/вопросом, а что — фактом.
- Пустой блок не рендерится.

### Downside / откат

- Откат — удалить тип и маркировку.

## PT08 — Калькулятор экономики (RoiCalculator)

**Категория:** интерактивная библиотека блоков. **Зависит от PT02.**
**Принцип эталона:** `PROPOSAL_COMPONENTS §3.3` — `RoiCalculator` (сравнение стоимости ручной работы и нового контура).
**Файлы:** новый интерактивный рендерер + редактор; `types.ts`.

### Контекст

PRISMA не показывает экономику. Для решений «руками vs контур» это сильный аргумент.

### Изменения

1. Данные: входные параметры (объём операций, стоимость операции вручную, доля автоматизации) + формула. Конфигурируется менеджером, считается у клиента в браузере.
2. Рендерер — форма + результат «было/стало/экономия в месяц». Стили PT01.
3. Опционально — трекинг взаимодействия (переиспользовать `public-events`, новый `eventType`, либо `metadata`).

### Критерий приёмки

- Клиент меняет вход → пересчёт в реальном времени. Дефолтные значения берутся из данных блока, не выдуманы.

### Downside / откат

- Откат — удалить тип. Никаких серверных зависимостей.

## PT09 — Конфигуратор сметы и выбор варианта (EstimateConfigurator / VariantPicker)

**Категория:** интерактивная библиотека блоков. **Зависит от PT02.**
**Принцип эталона:** `PROPOSAL_COMPONENTS §3.3` — `EstimateConfigurator`, `VariantPicker`, `ComparisonTable` (клиент сам собирает старт / выбирает архитектуру и видит компромиссы).
**Файлы:** новые интерактивные рендереры + редакторы; `types.ts`; учесть существующий трекинг `package_selected`.

### Контекст

Сейчас единственная интерактивность для клиента — выбор одного из пакетов. Нет модульной сборки и нет осознанного выбора между вариантами с подсветкой компромиссов.

### Изменения

1. `estimateConfigurator`: список модулей `{ name, price, dependsOn?, default }` с авто-пересчётом суммы и учётом зависимостей.
2. `variantPicker`: 2–4 варианта архитектуры с карточками компромиссов + связанная сравнительная таблица.
3. Расширить трекинг: фиксировать собранную конфигурацию/выбранный вариант (через `public-events` `metadata`, без новых таблиц).

### Критерий приёмки

- Клиент собирает конфигурацию/выбирает вариант, сумма и сводка пересчитываются; выбор уходит в события.
- `npm run build` ОК.

### Downside / откат

- Сложнее остальных блоков; можно дробить на два PR (configurator, picker). Откат — удалить типы.

## PT10 — Медиа и скриншоты как артефакты доверия

**Категория:** презентация, доказательность. **Зависит от PT02.**
**Принцип эталона:** `DESIGN_SYSTEM §5.5` + `PROPOSAL_COMPONENTS §3.4` — `ScreenshotFigure`, `ImageShowcase` (скриншоты/схемы/wireframes с коммерческой ролью, а не декор).
**Файлы:** новый рендерер + редактор; `proposal-store.ts`; `supabase/schema.sql` / Supabase Storage; [docs/deploy-docker-caddy.md](deploy-docker-caddy.md).

### Контекст

`proofItems` — только текст (title/description/result). Нет загрузки изображений и медиа-блоков. Для «презентации» это крупный пробел.

### Изменения

1. Хранилище изображений: Supabase Storage (bucket для КП). При локальном сторадже — каталог в `.data/` или внешний URL.
2. Блок `media`: одиночный `ScreenshotFigure` (картинка + подпись + `alt`) и галерея `ImageShowcase`.
3. Загрузка/удаление в редакторе; на публичной странице — затемняющий градиент под текст по `DESIGN_SYSTEM §5.5`; осмысленный `alt` обязателен.
4. Обновить **Resource profile** (storage/диск) в `docs/deploy-docker-caddy.md`.

### Критерий приёмки

- В КП можно прикрепить скриншот с подписью/alt; он рендерится на публичной странице.
- Учтён ретеншн: при архивации/очистке КП связанные медиа тоже убираются (см. `proposal-retention.ts`).

### Downside / откат

- Новый внешний ресурс (storage) — учесть в деплое и ретеншне. Откат — удалить тип `media` и bucket.

## PT11 — Контентные guardrails перед публикацией

**Категория:** качество контента.
**Принцип эталона:** `NEW_KP_INSTRUCTION §9` чек-лист; `AGENTS §2` жёсткие правила; `specs/content.md` тон без хайпа.
**Файлы:** [src/lib/proposal.ts](../src/lib/proposal.ts), [src/components/proposal/ProposalEditor.tsx](../src/components/proposal/ProposalEditor.tsx), [src/app/api/proposals/[id]/share/route.ts](../src/app/api/proposals/[id]/share/route.ts).

### Контекст

PRISMA публикует любой контент без проверок. Эталон требует проверяемого тона, явных границ, понятного следующего шага, помеченных допущений.

### Изменения

1. Функция-валидатор `checkProposalReadiness(proposal)` → список предупреждений:
   - пустой `nextStepText` (нет следующего шага);
   - пустые границы (`outOfScope`) при непустом скоупе;
   - стоп-слова хайпа («революционно», «уникально», «ИИ всё сделает сам», «волшебн…») — мягкое предупреждение со ссылкой на `DESIGN_SYSTEM §3`;
   - пакеты без цены при `showPrices`.
2. Показывать предупреждения в редакторе и перед «Опубликовать» (не блокировать жёстко — предупреждать).

### Критерий приёмки

- При публикации КП без следующего шага/границ менеджер видит предупреждение.
- Проверки не мешают сохранять черновик.

### Downside / откат

- Эвристики, возможны ложные срабатывания на стоп-словах — держать как мягкие предупреждения, не блок. Откат — отключить вызов валидатора.
